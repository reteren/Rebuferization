# REVIEW-WINDOW — W18 review of the window and hotkey layer

Reviewed: `src-tauri/src/window/**`, `src-tauri/src/hotkey/**`, plus how
`lib.rs` and `commands.rs` drive them, against SPEC §4/§5 and DECISIONS.md.
Read-only; no source files were modified.

**Confidence: medium-high on the reading, unverified by execution.** All
findings are derived from the code path, not from running it. I could not
check without a second monitor / a second machine: real multi-monitor
behavior (negative coordinates, mixed DPI) beyond hand arithmetic; the
process's actual DPI awareness (the manifest is generated by Tauri — the
"physical pixels everywhere" assumption in position.rs is only correct if
the process is per-monitor-V2 aware, which I could not verify from source);
UIPI behavior against an elevated target; and hook callback timing under
load. Findings 1 and 2 reproduce on a single monitor; the rest are
configuration-dependent.

---

## Findings, most severe first

### 1. Paste injection is never verified against the live foreground — `SendInput` targets whatever has focus, not the cached window (SPEC 5.4's destructive case)

`window/paste.rs:66-92` (`send_paste`) + `window/mod.rs:38-41` (the cache).

`send_paste` restores the cached HWND, sleeps 40 ms, then calls
`SendInput(Ctrl+V)`. `SendInput` does not address an HWND — it injects into
the input stream and lands in the window that has keyboard focus at
delivery time. Nothing between the cache and the injection re-checks that
the cached HWND (a) is still a live window (`IsWindow`), (b) is still the
foreground window, or (c) is not our own popup. `restore_foreground_window`
(paste.rs:39-58) also never verifies liveness, so its failure is silent.

Failure scenarios:

- **Target dies while the popup is open.** Cache = Word; Word crashes or is
  killed (Task Manager) while the popup is up; the user clicks a card.
  `SetForegroundWindow` fails, `AttachThreadInput` finds no thread, and
  `SendInput` delivers Ctrl+V into whatever Windows happens to have focus
  after the hidden popup releases it — the shell, the taskbar, a random
  window. The clipboard content (possibly a password) is pasted there. This
  is exactly what SPEC 5.4 calls destructive, and nothing in the code
  detects it.
- **The 40 ms settle is a race, not a guarantee.** Click a card
  (`closeOnCopy` defaults to true, so the popup vanishes), immediately
  click another window or re-press Alt+V: whatever grabbed focus during the
  40 ms receives Ctrl+V. The re-press variant lands the paste *in the
  popup's own search box*, dumping the clipboard text into the UI.
- **HWND recycling.** A stale HWND can be reused by Windows for an
  unrelated window; restore then raises an innocent app.

Fix direction (for the author): before injecting, verify `IsWindow(hwnd)`
and `GetForegroundWindow() == hwnd`; if either fails, log and skip the
injection rather than pasting into an unknown target.

### 2. Every dismissal steals focus back from the window the user just clicked

`window/mod.rs:54-69` (`hide_popup`) + `window/paste.rs:39-58`.

`hide_popup` unconditionally calls `restore_foreground_window()` on *every*
hide, including the outside-click dismissal (`Focused(false)` handler,
mod.rs:88-94). The popup activates per DECISIONS.md, so when the user
dismisses by clicking another application, that application briefly
activates, the popup sees focus loss and hides, and `SetForegroundWindow`
then yanks focus back to the *cached* window — which is not the one the
user clicked.

Failure scenario: popup open with Word cached → user clicks the browser →
the browser's activation is undone within ~10 ms and Word is raised. The
user's click does not land; they must click the browser a second time. This
happens on every click-away dismissal, on every machine including the one
that "works" — it is the single-monitor-visible version of the bug. The
restore is required only for the paste path; dismissal should leave the
newly activated window alone (and if the cached HWND is stale/recycled, the
restore raises an unrelated window — see finding 1).

### 3. Aggressive-mode hook silently swallows a chord press without firing it (dead press, no log)

`hotkey/llhook.rs:133-137`.

The re-arm lives in the *keyup* branch, and that branch is only reached
when the keyup's modifier state still matches the chord (`mods_match`,
llhook.rs:130). If the user releases the modifier before the key — a rolled
press: press Alt, press V, release Alt, release V — the V keyup fails the
modifier match, is passed through, and `hook_armed` stays `false`. The next
full Alt+V press then matches at llhook.rs:140, `hook_armed.swap(false)`
returns false, and the keystroke is swallowed with **no `WM_APP_TRIGGER`
posted**: the popup does not open, and nothing is logged — the exact
"hotkey does not work" symptom the codebase already treats as the hardest
failure to diagnose. It self-heals one press later (the dead press's own
keyup re-arms it), which makes it look intermittent. The re-arm should be
keyed on the chord key's keyup regardless of modifiers (or on the modifier
keyup).

### 4. Fixed-size mode overflows the work area; the clamp order then puts the excess on the right/bottom edge — onto the next monitor

`window/position.rs:40-51` (clamp order) + `window/position.rs:120-137`
(`window_size`).

The clamp is right/bottom first, then left/top, so when the window is
*wider* than the work area, the left clamp wins and the window sticks out
past `work.right`. The settings UI allows fixed sizes up to 3840 px
(Settings.svelte) and `window_size` scales by the target monitor's DPI, so
the window can exceed any work area.

Failure scenarios:

- 1366×768 laptop, sizeMode `fixed` at anything ≥ 1366 (e.g. 1440×900, or a
  size the user set for their desktop): x clamps to `work.left`, the right
  ~74 px of the popup are off-screen (or on the second monitor if one is to
  the right).
- Mixed DPI: fixed 1600×900 set on a 100% monitor, cursor on a 150%
  monitor → 2400×1350 physical on a work area that is 1920 wide at 100% →
  ~480 px spill. The same number is correct in the other direction (150% →
  100%), which is why the author's one-configuration test passed.
- Vertical monitor: width is the short side, so any fixed width ≥ the
  monitor's physical width spills.

Everything else on the SPEC 5.1 list **does hold**, verified by arithmetic:
percent mode derives size from the work area itself so it cannot overflow
(≤100% clamps at 1–100); negative coordinates from a monitor left of or
above the primary are handled by the `x < work.left` / `y < work.top`
clamps; DPI is read (`GetDpiForMonitor`) before clamping; the cursor at the
extreme bottom-right clamps correctly; a taskbar on the left edge is handled
(the cursor over it clamps up to `work.left`). Only the fixed-size
overflow is broken.

### 5. The UIPI guard is dead code — the SPEC-mandated log never fires

`window/paste.rs:83-90`.

`SendInput` returns the number of events inserted into the *system* input
stream; UIPI filtering happens at the destination window and does not
change the return value. When the target is elevated and Rebuffer is not,
`sent` is 2, the `sent == 0` branch never runs, and the failure is
completely silent — which is the opposite of SPEC 5.4's "UIPI failure
logged". The check only catches real `SendInput` failures (invalid
parameters). Correct detection requires comparing the foreground window
before/after injection (or checking `GetLastError`/integrity levels) — the
author should treat this branch as currently untestable dead code.

### 6. Modifier state is not cleared before Ctrl+V — the chord's own modifiers are still physically down

`window/paste.rs:76-83`.

The injected sequence is only Ctrl-down, V-down, V-up, Ctrl-up. If the user
still holds Alt (standard Alt+V) or Win (aggressive Win+V) when the card
click happens — common on the first quick interaction, since the hand is
still coming off the keyboard — the target receives Alt+Ctrl+V or
Win+Ctrl+V instead of Ctrl+V. In Word, Alt+Ctrl+V opens the Paste Special
dialog instead of pasting; Win+Ctrl+V is ignored by most applications, so
the paste silently does nothing. Check `GetAsyncKeyState` for the four
modifiers before injecting and synthesize the missing keyups.

### 7. Rebind failure paths leave a dead hotkey or a lying settings file

- `lib.rs:119-133` — the "fall back to Alt+V" logic covers *parse* failures
  only. A chord that parses but that `RegisterHotKey` refuses
  (`hotkey/mod.rs:591-598`, which only logs `tracing::warn!`) leaves the app
  running with **no hotkey at all** until the user touches settings. The
  `is_system_reserved` list is a UI warning, not a runtime guard; a
  hand-edited settings.json or a UI that lets a reserved chord through
  produces a tray app whose primary input is dead, logged only in a file.
- `hotkey/mod.rs:393-417` — when the hook thread's readiness `recv_timeout`
  fires, `rebind` returns `Err` **without clearing `aggressive`** and
  without re-registering the standard path (the degrade branch at
  mod.rs:400-411 handles `Ok(Err)` but not the timeout). The chord is
  unregistered and the hook may never arrive → dead hotkey until the next
  rebind.
- `commands.rs:163-180` — `update_settings` calls `settings.patch()` (which
  writes settings.json atomically) *before* `Chord::parse`. An unparseable
  binding is persisted and returned to the UI while the runtime keeps the
  old chord: the settings window shows a binding that is not the one in
  effect, and the next launch silently substitutes Alt+V (lib.rs fallback).
  Parse the chord before patching.

### 8. The hidden hotkey window is never destroyed and its class never unregistered (by the letter only)

`hotkey/mod.rs:422-452` (`Drop`). The drop path stops the hook thread,
calls `UnregisterHotKey`, posts `WM_QUIT`, and joins the window thread —
but the window thread exits without `DestroyWindow` (spawn_window_thread,
mod.rs:456-531) and the class registered at mod.rs:467-486 is never
`UnregisterClass`'d. Because `HotkeyManager` lives in `AppState` and is
dropped only at process exit, Windows reclaims both — the practical impact
is zero today, but if the manager is ever re-created (the `OnceLock` at
mod.rs:58 already forbids it), the class registration would collide. Also
worth noting the "message-only" window is actually a zero-style top-level
window (mod.rs:489-503), which is fine for `RegisterHotKey` but is not
`HWND_MESSAGE` as the module comment claims.

### 9. Settings window centering is unclamped — lands off-screen on small work areas

`window/position.rs:65-87` (`center_on_cursor_monitor`). No clamping at
all: a 960×660 settings window (tauri.conf.json) centered on a 1024×768
work area gets x = -32; on a 150% monitor with a small physical work area
it can be worse. SPEC 5.1's "never above workArea.left/top" applies only to
the popup; the settings window is the same codebase's other half.

### 10. `show_popup` toggles — the SPEC reference is what is wrong, not the code (and the check can race)

`window/mod.rs:30-34`. The tray's left-click and the single-instance plugin
both route through `show_popup`, which closes the popup when it is already
visible. **Correction to the review itself:** the toggle is the intended
behavior — pressing the hotkey again to dismiss is what Win+V does and what
users expect — so SPEC §8's "left-click opens the popup at the cursor"
should be read (or amended) as "toggles the popup", and the single-instance
plugin "surfaces the existing instance" by either opening or closing it,
which is fine. The genuine defect is narrower: `show_popup` runs on both
the hotkey window thread and the main thread (tray, second instance), and
the `is_visible` check is racy, so a tray click while a hotkey show is in
flight can hide the popup the hotkey just showed (or two shows can race
each other).

## Verified clean (checked, found nothing wrong)

- **Hook callback discipline.** `ll_hook_proc` (llhook.rs:110-150) touches
  only atomics, `GetAsyncKeyState`, a pointer deref of the system-owned
  `KBDLLHOOKSTRUCT`, and `PostMessageW`/`CallNextHookEx` — no allocation,
  no logging, no lock. Complies with the timeout rule.
- **No double-fire between hook and `RegisterHotKey`.** The rebind
  sequencing is correct in both directions: leaving aggressive mode joins
  the hook thread *before* the standard registration is applied
  (mod.rs:372-377); entering aggressive mode unregisters the standard path
  (synchronous `SendMessageW`) *before* the hook installs (mod.rs:393-417).
  `MOD_NOREPEAT` plus the `hook_armed` swap prevent hold-repeat refires.
- **Multi-monitor arithmetic for percent mode** (all SPEC 5.1 cases except
  the fixed-size overflow in finding 4): negative coordinates, mixed DPI
  (scale read before clamp), cursor at extreme bottom-right, left-edge
  taskbar, vertical monitors.
- **Lifetime:** `UnregisterHotKey` is called on every re-registration path
  and on drop; the window thread persists across rebinds (no leak on
  settings change); the hook thread is joined on rebind and drop; the
  `WorkerGuard` is bound to `AppState._log_guard`, not to a local. No
  guard-before-owner drops found in this scope.
- **Paste timing:** 40 ms settle is inside SPEC's 30–50 ms window, and the
  delay correctly sits after the restore.

## Resolution (W20)

All fixes below are confined to `src-tauri/src/window/**` and
`src-tauri/src/hotkey/**` plus this document; no other source was touched.

### 1. Paste into an unverified target — FIXED

`window/paste.rs` (`send_paste`): after the 40 ms settle the injection is
gated on `IsWindow(hwnd)` and `GetForegroundWindow() == hwnd`; either
failing logs at `warn` and skips the injection entirely — the clipboard
write has already succeeded, so the user pastes by hand. The cache is also
guarded at capture time (`window/mod.rs:53-62`): a foreground HWND that is
our own popup or settings window clears the cache instead of being stored,
which covers the show/hide race where the cache could have been our own
window. Testable parts: the gating is FFI against live windows, so it is
**not unit-tested**; the cache-guard is exercised only by code review.

### 2. Dismissal steals focus — FIXED

`window/mod.rs`: `hide_popup(&app)` keeps its signature and restore
behavior (command paths: Esc, close-on-copy, paste — we are the reason
focus left). A new `hide_popup_dismissed(&app)` hides without restoring and
is used by the outside-click handler (`Focused(false)`), where the window
the user clicked already has focus. **No commands.rs call-site change is
needed** — `paste_to_previous_window` and `commands::hide_popup` both keep
calling `hide_popup`, which is exactly the restore-intent they want.
Not unit-testable (window events), exercised by review only.

### 3. Rolled press swallowed by the hook — FIXED and TESTED

`hotkey/llhook.rs`: the decision was extracted into a pure state machine
`decide_hook(armed, vk_is_chord, is_up, mods_match)`, and the keyup of the
chord key now re-arms the hook **regardless of modifier state** (a matching
keyup is still swallowed; a mismatched one passes through — re-arming is
what matters). Six unit tests cover the normal press, auto-repeat, rolled
release, and full cycles (`llhook.rs::tests`).

### 4. Fixed-size overflow — FIXED and TESTED

`window/position.rs`: new pure helpers `clamp_size_to_work` and
`clamp_pos_to_work`; the size is clamped to the work area before the
position is clamped, so the right/bottom-then-left/top order can no longer
push the excess past the right edge. Five unit tests cover oversized fixed
windows, negative-coordinate monitors, the bottom-right cursor, and a
left-edge taskbar (`position.rs::tests`). The DPI-scaling of fixed sizes is
unchanged and was already correct.

### 5. UIPI guard is dead code — FIXED

`window/paste.rs`: the `sent == 0` check cannot detect UIPI (SendInput
reports success even when the elevated target filters the input), so
`send_paste` now compares the target process's mandatory integrity level
with ours (`OpenProcess` + `OpenProcessToken` + `GetTokenInformation`
`TokenIntegrityLevel`, last SID sub-authority) before injecting; when the
target is more elevated it logs the SPEC-mandated `warn` and skips, and
when the comparison cannot be made it logs that and injects anyway. The
`sent == 0` branch stays as a catch-all for genuine SendInput failures.
The required `Win32_Security` feature was added to `src-tauri/Cargo.toml`
by the coordinator and is confirmed present. **Not unit-testable** without
a live elevated process.

### 6. Chord modifiers still down at Ctrl+V — FIXED and TESTED

`window/paste.rs`: `send_paste` reads the active chord
(`hotkey::active_chord`, new in `hotkey/mod.rs`) and checks the physical
state of each of its modifiers with `GetAsyncKeyState` — checking, not
assuming; only modifiers actually held are released, as key-ups, before the
Ctrl+V sequence (order: Ctrl, Alt, Shift, Win; the Win key-up uses the
side that is down). No key-downs are synthesized for released modifiers,
and nothing is restored afterwards. `build_paste_events` is a pure function
with five unit tests (`paste.rs::tests`).

### 7. Failed rebind leaves a dead hotkey or a lying file — FIXED

`hotkey/mod.rs`: `rebind` is now fail-closed — it snapshots the previous
binding, and if the new one cannot be registered (RegisterHotKey refusal —
now reported back through the `WM_APP_REBIND` reply — or hook install
failure/timeout), it tears down whatever the failed attempt left running
and re-applies the previous binding, then returns `Err`. **Chosen failure
mode: the previous hotkey keeps working.** Rationale: a dead hotkey is the
state this codebase already treats as the hardest failure to diagnose, and
a working old chord plus an `Err` the UI can surface is strictly safer than
an honest file and no hotkey. The file half is closed too: `commands.rs::update_settings`
parses the chord before persisting anything, and rolls the hotkey section
of settings.json back to the previous binding when `rebind` fails, so the
file and the runtime cannot disagree. The startup path in `lib.rs` is
unchanged: a registration refusal still logs and leaves the app hotkeyless,
but now `rebind` reports it as an `Err` instead of a log-only warn. Not
unit-tested (needs real hotkey registration); exercised by review.

### 8. Hidden window never destroyed / class never unregistered — NOT CHANGED, by design

The drop path already stops the hook thread, calls `UnregisterHotKey`,
posts `WM_QUIT`, and joins the window thread. Adding `DestroyWindow` would
require a message round-trip to a thread that is being torn down at process
exit for zero benefit (Windows reclaims the HWND and the class at process
exit, and the `OnceLock` forbids ever re-creating the manager). Writing an
honest "not worth fixing" rather than adding shutdown-ordering risk.

### 9. Settings centering unclamped — FIXED and TESTED

`window/position.rs`: `center_on_cursor_monitor` now clamps the rescaled
size through the same `clamp_size_to_work` helper before centering, which
puts the window fully inside the work area (the centering formula is
in-bounds once the size fits). Covered by the size-clamp unit tests.

### 10. Show/hide race — FIXED; toggle kept; SPEC reference corrected

Toggle kept (hotkey-again-dismisses is Win+V behavior). `window/mod.rs`
adds a static `SHOW_LOCK` held by `show_popup` across the visible-check and
the show transition, serializing the two concurrent show paths (hotkey
thread and main thread). The dismissal handler uses `try_lock` and gives up
when a show is in flight — it must never block on the lock, because the
hotkey thread holds it across `win.show()`/`set_focus()` and a main thread
blocked on the lock instead of servicing window messages would deadlock
(that hazard is documented on the static). The review's finding-10 text was
corrected to say the toggle is intended and SPEC §8's wording should be
amended, not the code. Not unit-testable (window events and cross-thread
timing).

### What could not be tested

The injection path as a whole (findings 1, 2, 5, 10) needs live windows,
an elevated process, or two monitors; those are covered by review plus the
pure-logic tests where the logic could be extracted (hook state machine,
clamp arithmetic, event synthesis). `cargo test` / `cargo check` results
depend on the coordinator's answer to the pending `ask` (the
`Win32_Security` feature); everything else compiles clean.
